# Phase 2 task list with acceptance criteria

Derived from the web app's behaviour (`public/js/gpx.js`, `itinerary.js`, `app.js`
`insertManualStop` / `runOptimizer` / `renderOptimizer*`, `api.js getSuperchargersNear`) and the
feature map rows 23, 28, 30, 31, 32. Order is cheapest-first; each task ends in a commit.

## P2-1. GPX export
Core `GPXBuilder` (Foundation-only) + "Export GPX" in the briefing menu via the share sheet.
- **AC:** output matches the web `buildGPX` byte for byte apart from the metadata `<time>`
  (expected strings generated by running the web JS through `tools/web-reference/gen.mjs`):
  GPX 1.1, one `<wpt>` per stop with `lat`/`lon` to 6 decimals, ISO-8601 UTC `<time>` (ETA),
  `<name>` "Origin — …" / "Stop n — …" / "Destination — …", `<desc>` "72°F Partly cloudy ·
  wind 12 mph · precip 20%" (+ "OVERNIGHT STOP"), omitted when there is nothing to say; one
  `<trk>` with every route coordinate; XML special characters escaped.
- **AC:** the shared file is named after the trip (`Denver → Dallas.gpx`, unsafe characters
  replaced) and works offline from a cached briefing.

## P2-2. Navigate to a stop
Web's phone itinerary is dropped; each stop card gets "Navigate" with Apple Maps and Waze.
- **AC:** Waze opens `waze://?ll=<lat>,<lon>&navigate=yes` (6 decimals) when installed, else
  the web itinerary's link `https://waze.com/ul?ll=<lat>%2C<lon>&navigate=yes&zoom=17`
  (5 decimals); Apple Maps opens driving directions to the stop's coordinate with the stop
  label as the destination name.
- **AC:** the origin card has no Navigate button.

## P2-3. Manual stop entry
"Add a stop" field on the briefing (web `manualStopInput`): geocode the text, project it onto
the route, insert with the default 15-min dwell, fetch its forecast + alerts, persist.
- **AC:** an address within the corridor is snapped (`offRouteMi` reported, status message says
  "snapped to route" under 1 mi else "~N mi off route"); later stops' ETAs shift; the stop is
  `kind == .manual`, survives Save + reload and relaunch (replayed from `StopEdits`).
- **AC:** a failed geocode shows an error and changes nothing; the field clears on success.

## P2-4. Best-time-to-leave optimizer
`OptimizerView` from the briefing: window defaults to [departure, departure + 12 h];
`DepartureCandidates` picks the departures; each candidate (× each found route when there are
several) is briefed off-screen and scored with `TripScorer`.
- **AC:** candidate count and spacing equal the web formula (Core tests already pin it); one
  route → list ranked by score, best first and tagged; several routes → departure × route
  matrix with ★ on the best cell; each result shows arrival in the destination's zone and the
  worst condition with its nearest stop.
- **AC:** progress shows n / N; a failed forecast counts as unknown weather (penalty) rather
  than aborting; Cancel stops further calls.
- **AC:** choosing a result sets the departure (and route) and regenerates the briefing;
  the optimizer itself never replaces the on-screen briefing or the saved drafts.

## P2-5. Superchargers (Open Charge Map)
`OpenChargeMapService` (key from the Keychain) and a `Charger` model in Core.
- **AC:** for an EV vehicle with a key, every stop except the origin gets up to 2 Tesla
  (`operatorid=23`) chargers within 30 mi: name, distance (0.1 mi), town, stalls, max kW —
  parsed exactly like the web's `getSuperchargersNear`; the first is shown on the stop card.
- **AC:** no key or a non-EV vehicle → no OCM requests at all; any OCM failure → no chargers,
  the briefing still succeeds, and the Data Sources OCM row records the error.
- **AC:** chargers are persisted with the briefing (`StopRecord.chargersData`) and shown offline.
